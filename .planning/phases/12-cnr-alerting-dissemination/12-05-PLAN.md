<objective>
Add the 3-tier throttle and the hourly PMESII-grouped digest to the proven emitter path.

Implements D-03 verbatim: the alerting service runs its own asyncio hourly tick — no scheduler
container coupling, no piggybacking on the next alert — publishing exactly one grouped digest message
when suppressed alerts exist since the last digest, and nothing at all for an empty hour. Consumes
the sliding-window and digest-bookkeeping Store methods landed by D-02 in plan 12-02.

Covers SPEC R3 in full. Roadmap requirement: ADR-003 §Dissemination.

Purpose: make overflow visible rather than lossy. SPEC R3's hard property is that a throttled alert
is never silently dropped — it is collapsed into a digest that enumerates it — so the throttle and
the digest are one indivisible unit of work.

Output: sliding-window throttling wired into the emit path, and an hourly digest task in the worker.

    returning a small verdict object carrying a boolean pass flag and, when throttled, the tier name
    that tripped, so the log line and the digest reason are specific.

    The counting rule must be stated explicitly in the module docstring, because it is the
    likeliest off-by-one in the phase: `claim_alert` has already written this alert's row with its
    fired_at before the throttle runs, so `count_alerts_in_window` includes the alert currently being
    evaluated. The pass condition is therefore a strict greater-than comparison — the alert passes
    when the count is at most the cap, and is throttled when the count exceeds it. That yields
    exactly SPEC R3's boundary: the 5th alert sees a count of 5 and passes, the 6th sees 6 and is
    throttled. Evaluate the 60-second tier first, then the 600-second tier; report whichever trips.

    Both windows are sliding by construction — the Store method compares fired_at against the
    injected-or-server now minus an interval, never against a truncated calendar boundary. Do not
    add any bucketing, rounding, or period-start caching; that reintroduces the burst loophole SPEC
    R3's precision edge names.

    enrichment table), log at info with the item id and the tripping tier, and return without any

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| alert volume → ntfy egress | Burst volume is the DoS surface the throttle exists to bound |
| suppressed rows → digest message body | Item titles from remote sources are rendered into the push body |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-23 | Denial of Service | ntfy egress under an alert flood | high | mitigate | Two sliding-window caps evaluated before any egress; boundary asserted at 5-per-60s and 10-per-600s. The caps must not be weakened — they are the mitigation, not a tuning knob |
| T-12-24 | Repudiation | a throttled alert vanishing without a trace | high | mitigate | Every throttled alert is marked suppressed and enumerated by alert_id in the next digest; the digest marks rows only after a successful delivery, so a failed digest retries rather than consuming them |
| T-12-25 | Denial of Service | the digest tick itself becoming an unbounded message | medium | mitigate | One message per hour maximum by construction; the tick emits nothing for an empty hour and cannot be triggered by an incoming event (D-03) |
| T-12-26 | Information Disclosure | remote-sourced item titles rendered into the push body | low | accept | Titles already flow to the operator's Obsidian vault and the SAB through existing paths; ntfy renders plain text, and the digest adds no new rendering surface |
| T-12-27 | Denial of Service | an exception in the tick killing the task silently | medium | mitigate | The loop catches and logs per iteration, matching the wiki periodic task's shape, so one bad hour does not stop future digests |
| T-12-SC | Tampering | pip installs | high | accept | No package installs in this plan |
</threat_model>
