<objective>
Make the egress path lossless: in-process retry with the SPEC-locked 1s then 5s backoff, terminal
dead-lettering to a dedicated alerting queue, and an audit row on every terminal failure.

Implements SPEC R4 (outbox + DLX, no alert lost) using ADR-007's existing RabbitMQ topology idioms as
the substrate, per SPEC §Constraints. Follows RESEARCH Pattern 5's recommendation of an in-process
retry loop over the TTL-and-DLX chain recipe: SPEC does not require retries to survive a mid-backoff
process restart, and the broker-outage case is already covered by unacked redelivery, so the extra
wait queues would add topology risk for no acceptance-criterion gain.

Roadmap requirement: ADR-003 §Dissemination.

Purpose: an alerting system that silently swallows a failed push is worse than none. This plan makes
every terminal failure land somewhere an operator can find it.

Output: a retrying outbox with a dedicated dead-letter destination and an audit trail.

## Assumption A3 carried forward from RESEARCH

RESEARCH assumption A3 records that the in-process retry loop satisfies SPEC R4 without the RabbitMQ
TTL-and-DLX chain. The risk if wrong is a process crash mid-backoff losing the in-flight retry — which
this plan neutralizes by acking the trigger message only after the outcome is durably recorded, so a
crash mid-backoff leaves the message unacked and the broker redelivers it. Recorded here so the
tradeoff is visible rather than assumed.

    `deliver_with_retry(client, store, bus, payload, *, item_id)` runs the attempts, treating both a
    non-2xx response and a transport-level connection error as a failure. On success it calls the
    Store's outcome method with the delivered outcome and returns. On exhaustion it calls
    `dead_letter(...)`.

    `dead_letter(store, bus, payload, *, item_id, reason, attempts)` does three durable things, in
    this order: publish the payload to the `outbox.dlx` routing key with the item id, carrying the
    full 7-field payload plus the failure reason and attempt count so the alert is reconstructable
    from the queue alone; write an audit row through the Store's audit method with an op naming the
    dead-letter event, the alert-state table as the table name, the item id, and details carrying the
    alert_id, the dedupe_id, the attempt count, and the reason; and record the dead-lettered outcome

    body or any credential.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| emitter → ntfy over HTTP | An unreachable or hostile-responding endpoint is the failure surface this plan handles |
| emitter → outbox.dlx.queue | The full alert payload is written to a durable broker queue |
| emitter → audit table | Terminal failures are recorded for operator review |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-28 | Repudiation | a failed push disappearing with no record | high | mitigate | Terminal failures publish to a dedicated dead-letter queue AND write an audit row AND stamp the alert-state row — three independent durable records, all asserted |
| T-12-29 | Denial of Service | unbounded retry against a dead endpoint | medium | mitigate | Exactly three attempts on a fixed 1s/5s schedule with a 10-second per-request timeout; no exponential escalation and no unbounded loop |
| T-12-30 | Information Disclosure | payload or credentials in error logs | high | mitigate | Log the item id and the reason only; asserted as a source criterion that no log call in the dead-letter path receives the payload or a credential |
| T-12-31 | Tampering | alerting failures buried in the shared project dead-letter queue | medium | mitigate | A dedicated queue distinct from the project-wide dead-letter queue, per SPEC R4 and the RESEARCH anti-pattern note |
| T-12-32 | Repudiation | acking a trigger before the outcome is durable | high | mitigate | The durable record is written before the emit path returns, so the process context has not yet acked; a crash leaves the message unacked for broker redelivery. Guarded by a comment against a throughput-motivated refactor |
| T-12-33 | Information Disclosure | full alert payload resting on a broker queue | low | accept | The broker is loopback-bound and already carries the same enrichment content on other queues; the payload must be complete for the alert to be reconstructable, which is the point of the dead-letter record |
| T-12-SC | Tampering | pip installs | high | accept | No package installs — the retry is a fixed two-element schedule rather than a new backoff dependency |
</threat_model>
